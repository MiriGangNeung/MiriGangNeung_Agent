# ADR-0006: 합성 전에 배경을 요청 비율로 잘라 넘긴다

- 상태: 채택
- 날짜: 2026-09-09 (KST)
- 관련: ADR-0002(배경 이미지 조달), ADR-0003(배경 사진 VLM 분석)

## 맥락

사용자가 안반데기 결과에서 "배추밭 구역의 픽셀이 뭉개졌다"고 지적했다. 원인을
픽셀로 확인했다.

- 배경 원본: 940×626 (가로 3:2, 한국관광공사 Type1)
- 결과: 921×1152 (세로 4:5, 프론트가 `aspectRatio`를 `'4:5'`로 고정)
- 배경을 결과 폭에 맞추면 세로 613px — **결과의 53%밖에 덮지 못한다.**

즉 나머지 47%는 모델이 지어낸 영역이었다. 원본과 결과의 행별 상관계수가 이를
그대로 보여준다.

| 결과 y좌표 | 원본과의 상관계수 |
|---|---|
| 0 (하늘) | +0.989 |
| 84 | +0.976 |
| 210 | +0.844 |
| 336 (밭 시작) | **+0.101** |
| 462 | +0.001 |
| 588 | −0.141 |

디테일(라플라시안 표준편차)이 가장 낮은 띠는 y 576~767이고, 이는 원본이 끝나는
경계 y≈613을 걸친다. **업스케일된 실제 픽셀과 창작된 픽셀이 만나는 자리**이며,
배추밭처럼 촘촘히 반복되는 질감은 생성 모델이 가장 못 버티는 대상이다.

기존 파이프라인은 배경을 손대지 않고 그대로 넘기면서 출력 비율만
`ImageConfig(aspect_ratio=...)`로 강제하고 있었다. 관광공사 Type1 사진이 거의 다
가로 3:2이고 서비스는 세로 4:5를 요청하므로, 이 어긋남은 특정 장소의 문제가 아니라
**모든 합성에 상시로 존재했다.**

## 검토한 선택지

1. **출력 비율을 배경에 맞춘다** — 화각 손실이 없지만 "인생샷은 세로"라는 제품
   결정과 충돌한다. 프론트가 `'4:5'`를 하드코딩하고 있어 계약 변경도 필요하다.
2. **배경을 업스케일해서 넘긴다** — 없는 디테일을 만들지 못하면서 모델에 "이 정도
   해상도의 정보가 있다"는 잘못된 신호만 준다. 창작 영역은 그대로 남는다.
3. **프롬프트로 "배경을 늘리지 말라"고 지시한다** — 늘리지 않으면 프레임을 채울
   방법이 없으므로 모순된 지시다.
4. **배경을 목표 비율로 미리 잘라 넘긴다** ← 채택

## 결정

`app/pipeline/background_fit.py`가 합성 직전에 배경을 요청 비율로 커버 크롭한다.
모델의 일이 "프레임을 47% 늘려라"에서 "이 프레임 안에 인물을 넣어라"로 바뀐다.

- 크롭 창은 `suggestedSubjectZone`의 좌우 힌트로 옮긴다. 인물을 세울 자리가
  왼쪽으로 판정됐는데 가운데를 자르면 정작 세워야 할 지면이 잘려나간다.
- **해상도는 올리지 않는다** (선택지 2의 이유와 동일).
- 크롭 후 짧은 변이 320px 미만이면 보정을 건너뛴다. 창작을 막자고 모델이 쓸 픽셀
  자체를 없애는 것은 손해다.
- 비율이 이미 1% 이내로 맞으면 손대지 않는다. 재인코딩 손실이 더 크다.

## 결과

- 안반데기 재생성에서 **모델이 지어내야 하는 면적 47% → 0%** (크롭 배경이 1152px
  중 1150px을 덮는다). 구간별 디테일 편차 17.4 → 14.0.
- 사용자가 지적한 뭉개짐 띠가 사라졌다.
- **화각의 47%를 잃는다.** 3:2를 4:5로 자르는 이상 피할 수 없다. 잘려나간 것은
  원본에 있던 진짜 픽셀이지만, 대안은 그 자리를 창작으로 채우는 것이었다.
- 근본적으로는 배경 비율에 맞춰 `aspectRatio`를 고르는 것이 낫다(가로 배경에는
  `1:1`). 이는 프론트의 결정이라 이 ADR의 범위 밖이다.
