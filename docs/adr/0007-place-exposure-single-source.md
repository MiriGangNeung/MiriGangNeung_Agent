# ADR-0007: 장소·사진 노출 기준의 단일 출처는 VLM 판정 결과다

- 상태: 채택
- 날짜: 2026-09-09 (KST)
- 관련: ADR-0003(배경 사진 VLM 분석), 노션 「배경 사진 VLM 사전 분석 리포트」

## 맥락

노션 리포트는 관광공사 Type1 이미지 159장을 두 축(설 자리 / 배경 매력도)으로 걸러
**23곳 / 64장**만 남기고, 백엔드 필터 설계로 두 가지를 "반드시 적용"하라고 명시했다.

1. `portraitViability == "low"`는 프론트에 노출하지 않는다.
2. 쓸 수 있는 사진이 0장인 장소(9곳)는 배경 선택지에서 제외한다.

그런데 실제 백엔드는 `PromptPlaceCatalog.java`에 **43곳**을 하드코딩하고 있었고,
주석이 "Notion **pose guide**"였다 — 즉 판정 결과가 아니라 **팀 포즈 조사 문서**를
손으로 옮겨 적은 것이었다. 대조 결과:

- 두 리스트 교집합: **15곳**
- 판정했는데 미노출: 17곳 (강문해변·송정해변·월화거리·허난설헌 생가터 등)
- 판정한 적 없는데 노출: 28곳 (강릉아트센터·노암터널·해파랑길 39/40/41코스 등)
- **"설 자리 없음"으로 판정된 헌화로·소돌아들바위공원이 그대로 노출 중**

원인은 명확하다. 판정 결과를 전달할 **경로가 문서뿐이었다.** 이 서비스가 노출하는
엔드포인트는 `/v1/generations` 4개와 `/health`, `/v1/meta`뿐이고,
`app/places/insights.py::viable_images()`는 "프론트에 노출할 후보를 고르는 용도"라고
적혀 있으면서 호출자가 0개인 죽은 코드였다. 백엔드가 손으로 옮겨 적는 것 외에
방법이 없었다.

## 결정

판정 결과를 **기계가 읽는 산출물**로 만들어 단일 출처로 삼는다.

```
place_insights.json ──scripts/export_place_filter.py──▶ assets/places/viable_places.json
                                                              │ (복사)
                        BackEnd  /data/viable-places.json ◀────┘
                          ├ PromptPlaceCatalog      : 장소 노출 (23곳)
                          └ PlaceCatalogSyncService : 사진 노출 (판정 통과분만)
```

적용 규칙 세 가지(스크립트에 고정):

1. `portraitViability != "low"`
2. `camera.perspective != "high-angle"` — 드론 항공샷. 리포트가 "한 건도 없어야
   하고 다시 나타나면 파이프라인을 의심하라"고 적어둔 값인데, 현재 JSON에 경포호
   1장이 남아 있어 이 규칙 없이는 23곳이 아니라 24곳이 된다.
3. `placement.standableSurface`가 비어 있지 않을 것

**조인 키는 장소명이다.** 백엔드 `Place.id`는 `@GeneratedValue(UUID)`라 DB를 새로
만들 때마다 값이 바뀌므로 `placeId`는 산출물에 넣지 않는다.

## 왜 API가 아니라 파일인가

에이전트에 `/v1/places/viable` 엔드포인트를 추가하는 방법도 있었다. 파일을 택한
이유는 이 데이터가 **배치 분석의 산출물이고 요청마다 바뀌지 않기 때문**이다.
런타임 의존을 만들면 에이전트가 죽었을 때 백엔드의 장소 목록까지 함께 죽는다.
대신 사본이 어긋날 수 있으므로 `--check` 옵션으로 차이를 확인할 수 있게 했다.

## 결과

- 재동기화 후 노출 장소가 43곳 → **23곳**, 장소별 사진 수가 판정 결과와 정확히
  일치한다(강문해변 5, 경포대·경포해수욕장·안목해변·향호해변·허난설헌 4 …).
- 설 자리가 없다고 판정된 장소가 더 이상 노출되지 않는다.
- **사본 동기화가 수동이다.** `place_insights.json`을 갱신하면 스크립트를 다시 돌려
  백엔드 리소스로 복사해야 한다. 자동화하지 않은 것은 두 레포가 분리돼 있고 갱신
  빈도가 낮기 때문이다.
- 리포에 커밋된 `place_insights.json`은 54장인데 노션은 64장이다. **장소 목록(23곳)은
  일치하지만 사진 수가 다르다** — JSON이 노션 생성 시점보다 오래된 버전으로 보인다.
  노출 장소에는 영향이 없어 이번 범위에서 다루지 않았다.
