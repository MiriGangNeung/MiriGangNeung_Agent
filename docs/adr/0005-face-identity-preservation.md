# ADR-0005: 얼굴 신원 보존

- 상태: 채택 (2026-09-02)
- 관련: `app/pipeline/face_identity.py`, `app/pipeline/regenerate.py`,
  `app/pipeline/face_reference.py`, `docs/adr/0003-place-image-vlm-analysis.md`

## 문제

합성 결과가 **다른 사람 얼굴로 나온다.** 업로드 사진에서 얼굴이 화면에서 차지하는
비중이 작으면 합성 모델이 얼굴을 복사하지 못하고 재구성한다.

`prompts/composition_v5.md`에서 Identity 절을 이목구비 단위로 다시 쓰고 "더 예쁜
일반적인 얼굴로 수렴"을 명시적으로 금지했는데도 3/3 실패했다. **프롬프트 지시만으로는
해결되지 않는다**는 것이 출발점이다.

## 결정

### 1. 신원 판정은 로컬 임베딩으로 한다 (Gemini 판정 아님)

`cv2.FaceRecognizerSF`(SFace, opencv_zoo, Apache-2.0)로 업로드 사진과 결과의 얼굴
임베딩 코사인 유사도를 잰다. CPU에서 0.2초, 비용 0, 새 파이썬 의존성 없음.

**Gemini의 `face_matches_subject`를 쓰지 않는 이유**: 판정이 퇴화했다. 실측에서
SFace 0.587·0.590짜리 결과 — 사람 눈으로 확인한 '같은 사람' 기준(0.549)보다 높은 것 —
에도 false를 돌려줬고, 5건 전부 같은 문구였다. ADR-0003에서 Qwen2.5-VL의 판정성
필드가 상수에 가깝다는 것을 확인하고 Gemini 재판정으로 고쳤는데, **그 Gemini도 같은
성격의 필드에서는 똑같이 퇴화한다.** 필드 자체는 payload에 남겨 관측용으로 쓴다.

검증: 사람 눈으로 매긴 순서(구룡폭포 > 정동심곡 > 송정)와 SFace 점수 순서
(0.571 > 0.458 > 0.269)가 정확히 일치했다.

### 2. 유사도가 목표에 못 미치면 다시 뽑는다

생성이 확률적이라 같은 입력도 매번 다른 얼굴이 나온다. `FACE_SIMILARITY_TARGET`(0.45)에
못 미치면 최대 `FACE_REGENERATE_MAX_ATTEMPTS`(3)번까지 다시 뽑고, 상한을 다 쓰면
그중 가장 닮은 결과를 채택한다.

**판정이 로컬이라 vision 호출 수는 늘지 않는다.** 늘어나는 것은 이미지 생성 호출뿐이다.
시도마다 품질 검사를 부르는 안은 작업 시간이 N배가 되어 기각했다.

### 3. 얼굴이 작게 찍힌 사진에는 얼굴 참조 이미지를 함께 넘긴다

`face_ratio`(얼굴 높이 / 이미지 높이)가 `FACE_RATIO_ASSIST_BELOW`(0.5) 미만이면
얼굴만 잘라 512px로 확대한 참조를 세 번째 이미지로 넘긴다.

**절대 픽셀이 아니라 비율로 판단한다** — 모델이 얼굴에 배정하는 표현 용량은 프레임
대비 크기를 따라가지, 원본 파일이 몇 픽셀인지를 따라가지 않는다. 고해상도 전신샷은
절대 크기가 커도 얼굴 비중이 낮다.

### 4. 얼굴이 달라도 거부하지 않는다 — 경고만 단다

재생성을 다 쓰고도 `FACE_SIMILARITY_WARN_BELOW`(0.30)에 못 미치면 결과를 그대로 주고
`safety.warnings`에 `FACE_NOT_PRESERVED`를 싣는다. **Job은 실패하지 않는다.**

얼굴이 화면에서 작게 찍힌 사진(`woman1.jpg`는 28%)은 흔한 여행 사진이고, 그걸 이유로
결과를 아예 못 받게 하면 정상 사용자가 대량으로 막힌다.

두 임계값을 나눈 이유: `target`은 "더 잘 뽑아보자"는 내부 기준이라 높게 잡아도
사용자에게 보이는 것이 없고, `warn_below`는 사용자를 귀찮게 하는 선이라 널널하게 잡는다.

## 근거 데이터 (2026-09-02)

사람 눈으로 라벨을 붙인 4장 + 기존 결과 23장을 로컬 채점해 정했다.

| 관찰 | 유사도 |
| --- | --- |
| 사람 눈으로 "명백히 다른 사람" | 0.269 |
| 사람 눈으로 "같은 사람" | 0.549 ~ 0.571 |
| SFace 문서 기준값 | 0.363 |
| 기존 결과 23장 중앙값 | male 0.479 / woman 0.400 |

E2E(`woman1.jpg` × 5개 장소, 도입 전 100% 실패):

| | 도입 전 | 도입 후 |
| --- | --- | --- |
| Job 성공 | 0/5 | **5/5** |
| 유사도 중앙값 | 0.400 (v4 결과 기준) | **0.467** |
| 유사도 최저 | 0.269 | **0.422** |
| 경고 | — | 0건 |
| 소요 시간 | ~30초 | ~45초 (시도 평균 2.2회) |

최저점이 올라간 것이 핵심이다. 파국적 신원 손실이 사라졌다.

## 검토했으나 채택하지 않은 것

**InstantID / IP-Adapter FaceID로 합성 자체를 대체** — 그 모델들은 얼굴 임베딩과
포즈로 이미지를 **새로 생성**하지, 실제 관광지 사진을 픽셀 그대로 보존하며 사람을
끼워 넣지 않는다. 배경 보존은 계약의 핵심이고 `BACKGROUND_ALTERED`로 게이트까지 걸어
둔 항목이라 맞바꿀 수 없다.

**GPU 얼굴 영역 복원(2단계 후처리)** — 합성 결과의 얼굴 상자만 잘라 신원 조건부
img2img를 돌리고 소프트 마스크로 되붙이는 방식. 얼굴 상자 밖이 안 바뀌므로 배경
보존이 구조적으로 보장된다. **설계는 유효하나 지금은 구현하지 않는다** — 위 재생성
루프만으로 5/5·경고 0건에 도달했고, T4에서 SDXL 파이프라인은 장당 30~60초라
실시간 경로에 넣기 어렵다. 재생성으로 부족해지면 이 경로로 확장한다.

## 운영 메모

- SFace 모델(38MB)은 리포에 커밋하지 않는다. `scripts/download_models.sh`로 받는다.
  **없어도 서비스는 동작한다** — 신원 판정과 재생성만 생략되고 합성은 1회로 끝난다.
  YuNet이 없어 Haar로 폴백하는 경우도 랜드마크가 없어 판정을 생략한다.
- 재생성 상한은 `GET /v1/meta`의 `faceRegenerateMaxAttempts`로 노출한다. 백엔드가
  폴링 타임아웃을 잡을 때 필요하다 — 이 값이 크면 한 Job이 그만큼 오래 걸린다.
- `estimatedCostUsd`는 실제 생성 호출 수를 곱해 기록한다.
